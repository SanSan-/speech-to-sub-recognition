## Context

Потребность описана в [предложении](proposal.md#why), наблюдаемое поведение — в
[дельте WEB-010](specs/local-web-workflow/spec.md).

До исправления в [общем сервисе](../../../../speech_to_sub/service.py) отбор кандидата исключал только `is_symlink()`,
затем разрешал путь. Junction на соседний каталог проходил последующую проверку родителя; маркер и возраст уже
проверялись у цели. Общий детектор `is_link_or_junction` существует в [io_utils.py](../../../../speech_to_sub/utils/io_utils.py)
и используется при поиске медиа. Прежние [тесты сервиса](../../../../tests/test_service.py) проверяли очистку обычных
устаревших, свежих, активных и неуправляемых каталогов, но не содержали сценария с реальным junction.

## Goals / Non-Goals

**Цели:** закрыть обход отбора кандидата и доказать сохранность цели настоящего NTFS junction в общем входе очистки.
Сохранить текущие условия допустимости обычного каталога и продолжение обхода после исключённой ссылки.

**Вне области:** изменение места `WORK_DIR`, новая политика для корня рабочей области, изменение маркера владения,
защита от конкурентной подмены каталогов другим процессом, исправление веб-выбора файлов и остальных разрывов.
Схема SQLite, настройки срока хранения и правила блокировок не меняются.

## Decisions

### Проверять исходный кандидат общим детектором

В `_stale_workspace_target` применить `is_link_or_junction` к исходному кандидату до `resolve()`.
Так ссылка исключается до обращения к маркеру и блокировке цели. Сохранить проверку префикса `job-`, непосредственного
родителя, обычного файла маркера и возраста `max(mtime каталога, mtime маркера)`; возраст должен строго превышать срок
хранения. Проверка активной блокировки остаётся в общем входе очистки.

Новый детектор не нужен: существующий уже различает символические ссылки и Windows junction. Проверка только после
разрешения пути непригодна, поскольку происхождение обычной цели как ссылки к этому моменту потеряно.
Усиление одного сравнения родителя не устраняет случай цели внутри того же `WORK_DIR`.

### Проверять реальный junction и обычный каталог в одном обходе

В `tmp_path` создать `work/user-data` с непустым маркером `.active.lock`, контрольным файлом и вложенным контрольным
файлом; `work/job-junction` направить на него. Имя цели не начинается с `job-`, поэтому она не может быть независимо
удалена как обычный управляемый каталог. Добавить отдельный `work/job-stale` с маркером для положительного контроля.

После подготовки содержимого задать времена каталога и маркеров 100 секунд, вызвать очистку с `now=1000`
и сроком хранения 100 секунд. Проверить список удалённых каталогов, сохранность junction и его прежней цели,
байтов маркера и обоих контрольных файлов; обычный `job-stale` должен быть удалён.
Существующая проверка активной блокировки, свежего каталога и отсутствующего маркера остаётся обязательной.

Junction создавать в Windows PowerShell 5.1 через `New-Item -ItemType Junction`, передавая только временные пути
без построения исполняемой строки из пользовательских значений. Проверить успешное создание настоящей ссылки.
Очистка фикстуры удаляет только сам junction нерекурсивно, после чего временные обычные каталоги убирает pytest.
На Windows ошибка подготовки не должна превращаться в успешный пропуск регрессии; на другой ОС допускается
явный пропуск только платформенного сценария. Подмена детектора не заменяет эту проверку на целевой Windows-среде.

### Сохранить существующий архитектурный контракт

Изменение восстанавливает принятое ограничение [WEB-010](../../../specs/local-web-workflow/spec.md#requirement-web-010-очистка-и-история)
и не меняет решение [ADR-004](../../../context/ADR/ADR-004-local-web-state.md). Новое ADR не требуется.
В основную спецификацию при реализации переносится полный изменённый WEB-010 с прежними сценариями и точными
относительными ссылками; другие требования сохраняются.

Проверки выполняются по [проектной процедуре](../../../../README.md#проверки), полный цикл анализа — по
[процедуре Sonar](../../../../README.md#sonar) и критериям
[ENG-004](../../../specs/engineering-constraints/spec.md#requirement-eng-004-анализ-sonar-и-граница-покрытия).
Финальный свежий анализ должен относиться к окончательному коду, тестам и синхронизированной версии при закрытии работы.

## Risks / Trade-offs

- Цель вне `WORK_DIR` не выявляет этот дефект: её уже отсекает проверка родителя → использовать соседнюю цель без
  префикса `job-`, старый маркер и отсутствие активной блокировки.
- Ошибка подготовки ссылки может скрыть отсутствие проверки → проверять реальный тип junction и считать сбой
  подготовки на Windows незавершённой проверкой.
- Удаление тестового junction может затронуть цель → все пути ограничены `tmp_path`; удаляется только сама ссылка
  нерекурсивной операцией, без передачи разрешённого пути цели в рекурсивное удаление.
- Проверка до разрешения пути не устраняет конкурентную подмену после проверки → такую защиту этот пакет не заявляет.

## Migration Plan

Миграция сохранённых данных и изменение настроек не нужны. После применения новые вызовы очистки будут пропускать
junction; ранее удалённые данные это исправление не восстанавливает.

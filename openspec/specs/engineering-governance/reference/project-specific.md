# Инженерное приложение speech-to-sub-recognition

Обязательно вместе с [общим профилем](python-common.md).

## Язык и изменения

Отвечай по-русски, используй «исправил». Выбирай минимальные инструменты и точечные изменения. В русском тексте
используй русские термины; буквальные идентификаторы, модели, команды и общепринятые сокращения сохраняй, при
необходимости объясняй. Учебный текст перечитывай на необъяснённые сокращения, скрытые предпосылки, скачки рассуждения и
служебные фразы. Комментарии, docstring и журналы — по-русски, кроме принятого в конкретном файле устойчивого стиля.

Читай и пиши с явной UTF-8 без BOM. Перед записью перечитай файл и проверь кодировку; не меняй её временно ради
проверки. Перекодирование требует прямого разрешения. Сохраняй существующие изменения. Текст существующих журналов не
изменяй без отдельного запроса. Не выполняй действий с Git без прямого указания.

## Разработка и принятие

Проверяй существующую реализацию до добавления новой. Соблюдай DRY, SOLID, KISS и YAGNI: один ответственный компонент,
именованные константы, небольшая функция с одной задачей (ориентир 40–50 строк), специализированные интерфейсы и
зависимость от абстракций. Не добавляй функции вне текущей задачи; удаляй ненужный код только в области принятой замены.

Принятое решение фиксируй вместе с изменением контракта. Обновляй связанные спецификации, примеры и параметры; если
синхронизация невозможна, сообщай причину. Для изменения поведения выполни применимые тесты, настроенные линтеры, сборку
или рабочую проверку; ошибки исправляй в пределах задачи. Изменение документации проверяется статически по общему
профилю.

## Настройки и компоненты

Полный компактный контракт параметров CLI, маршрутов API и состояний находится
в [application-interface.md](application-interface.md); он является нормативным приложением вместе с предметными
требованиями.

Порядок: defaults → .env без замены окружения процесса → явные аргументы. Новую переменную описывай в OpenSpec и
в [.env.example](../../../../.env.example) с переносимым значением; локальный .env и токены не публикуй.
Пользовательский README получает согласованную справку, но нормативный контракт остаётся в OpenSpec.

Точные значения по умолчанию принадлежат [constants.py](../../../../speech_to_sub/constants.py)
и [models.py](../../../../speech_to_sub/models.py): faster-whisper, language=en, audio_language=eng, aligner=none,
output_format=srt; веб 127.0.0.1:7862; long-form 300/2 секунды, VAD 600 мс, beam_size=5. Идентичность:
PIPELINE_VERSION=7, SIDECAR_SCHEMA_VERSION=2, SRT builder=4, ASS/VTT renderer=1.

При смене backend без явного пути выбирай его собственный каталог. Основная модель whisper-large-v3-ct2, Transformers —
запасной профиль; Parakeet/Qwen изолированы. Для локальной полной модели и совместимого кеша сеть запрещена; после
реального промаха недостающая модель докачивается в тот же каталог при разрешённой настройке, проверке места и
блокировке. Не менять механизм приобретения модели без изменения соответствующего контракта.

## Документы и доказательства

- openspec/specs — принятые требования, архитектурные контракты и критерии.
- openspec/changes — незавершённые задачи и датированное evidence; отметка задачи ставится только после проверки. После
  завершения итог сохраняется в evidence и CHANGELOG, закрытый change архивируется и исключается из активной очереди.
- openspec/context/ADR — значимые решения; examples — настоящие ссылки; failure-log — исправления контекста.
- README — переносимая пользовательская инструкция; требования описаны в OpenSpec.
- CHANGELOG — значимые реализованные изменения документации, поведения, зависимостей и правил, по версиям; «Не выпущено»
  отделяется от планов.
- docs/benchmarks — первичные данные измерений, не повторный набор требований.
- .env.example и sonar-project.properties.example — только переносимые примеры без секретов.

Используй в инструкциях плейсхолдеры <repo-root>, <media-file>, <media-directory>, <local-asr-model-path>, <
local-aligner-model-path>, <local-hf-cache>, <sonar-url>. Локальную установку и проверки держи ближе к концу
пользовательской инструкции; команды Windows и Linux/macOS/WSL разделяй. Перед отчётом проверяй Markdown-ссылки,
отсутствие противоречащих копий контракта и UTF-8 без BOM.

## Команды и ограничения проверок

Все команды выполняются из корня проекта; перечисление команды не означает её выполнения.

```powershell
.\.venv\Scripts\python.exe -B -m pytest
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m compileall -q speech_to_sub tests
node --check speech_to_sub\web\static\app.js
npm test
openspec validate --all --strict --no-interactive
```

Создание среды: py -3.14 -m venv .venv, затем проектный Python -m pip install -r requirements.txt; браузерная установка
npm ci. Эти команды меняют среду и не выполняются при обслуживании документации. Для Parakeet/Qwen используется
setup_workers.ps1 с -Parakeet/-Qwen. Запуск CLI — проектный Python -m speech_to_sub; веб — run_web.ps1 либо -m
speech_to_sub.web. FFmpeg/ffprobe должны быть доступны в PATH или по настроенным путям.

Тяжёлая проверка: явно задать RUN_LOCAL_ASR_TEST=1, ASR_TEST_MEDIA=<media-file>, ASR_TEST_LANGUAGE=en и запустить
проектный Python -B -m pytest -m integration. Отказные проверки и результаты размещать в тестовом каталоге; оригиналы не
менять. Сеть и облачная отправка требуют условий предметного контракта, а не следуют из запуска тестов.

## Sonar

Ключ speech-to-sub-recognition; безопасная
конфигурация — [sonar-project.properties.example](../../../../sonar-project.properties.example), адрес SONAR_HOST_URL,
токен только SONAR_TOKEN в локальном окружении. Нужны проектная среда, sonar-scanner, Node.js и доступный сервер.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .codex\skills\fix-sonar\scripts\sonar_cycle.ps1 -TimeoutSeconds 600 -RequireClean
```

Цикл создаёт свежий pytest-cov coverage.xml, запускает scanner, ждёт именно новой CE-задачи и проверяет Quality Gate,
SECURITY, открытые замечания, дублирование и порог покрытия. -SkipScanner проверяет прежний серверный анализ и не
доказывает новое дерево. Клиентская статика входит в анализ; без LCOV её нет в численном покрытии, Playwright
проверяется отдельно. Для будущего включения нужны instrumentation, LCOV, sonar.javascript.lcov.reportPaths и новая
проверка объединённой метрики; это условие расширения, а не обещание выполненной работы.

Отчёт в evidence действующего изменения: дата/срез, команды, CE ID/status, тесты/покрытие, Quality Gate,
замечания/SECURITY, дублирование, Ruff/pip/Node/Playwright и причины пропусков. При расхождении API/UI после SUCCESS
сначала повторно проверить API и ключ проекта; возможная дальнейшая диагностика чужого сервера только по его инструкциям
и без изменения состояния замечаний через SQL.

## Автоматические правила контекста

Обязательны [SEC-CONTEXT-001…004](../spec.md) и [CTX-005…008](../../project-context/spec.md): проверка существенного
плана, безопасные входы и передача, событийная сводка, ограниченный вывод, восстановление и смысловая дельта. Аудит
CTX-009 применяется только по отдельному явному запросу с заданной областью проверки. Локальный инженерный профиль
описан в python-common.md.

Датированные доказательства хранятся в соответствующем изменении. Отдельный аудит требует явного запроса с заданной
областью проверки. Полные процедуры навыков остаются в SKILL.md.
